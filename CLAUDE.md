# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

pwrde — a GPU-accelerated terminal workspace for macOS, written in Rust. Groups (vertical sidebar tabs) each hold a binary split tree of tiles; each tile has a horizontal tab strip of terminals (cmux-style). macOS-only.

The top-level pages (see `pages.rs`) are **Sessions** (the terminal workspace), one page per user-registered **CLI tool** (`cli_tools.rs` — a full-page, non-persisted terminal running e.g. `drop -d` from `~/src`; the built-in default replaces the old Cleanup page), and **Settings** (its own window, opened from the gear chip, ⌘, or `page settings`).

## Commands

- `cargo run --release` — build and run the app. Debug builds also work (deps are compiled at `-O2` even in dev, so it stays usable). Webview tabs also need the `pwrde-helper` bin, which `cargo run` alone does not build: run `cargo build` (every bin) first, with the same profile — see "Chromium (CEF)" below.
- `pwrde-cli <subcommand>` — drive a running app over the command bus (`pwrde-cli --help`). **Use the `/pwrde-cli` project skill (`.claude/skills/pwrde-cli/SKILL.md`) to verify changes against the real app** — dev-build launch, socket resolution, the command cheat-sheet, and the screenshot + `state` verification loop.
- `cargo test` — run all tests. Tests are inline `#[cfg(test)]` modules in `src/*.rs`; there is no `tests/` directory.
- `cargo test <name>` — run a single test or filter by substring.
- `scripts/make-app.sh` — assemble `target/release/Pwrde.app` (requires `cargo build --release` first). It bundles Chromium: `Contents/Frameworks/Chromium Embedded Framework.framework` (from `$CEF_PATH`, else the copy the build downloaded) and the five helper apps CEF launches subprocesses from (`Pwrde Helper.app` and its ` (GPU)` / ` (Renderer)` / ` (Plugin)` / ` (Alerts)` siblings, each an `Info.plist` plus a copy of `target/release/pwrde-helper`), and signs inside-out — the framework's libraries, the framework, each helper, then the app. Ad-hoc signed by default; with `PWRDE_SIGN_IDENTITY` + `PWRDE_TEAM_ID` + `PWRDE_PROVISION_PROFILE` it produces a Developer ID build under the hardened runtime: helpers get the JIT entitlements Chromium needs, the app is signed with `scripts/pwrde.entitlements.in`, whose restricted `web-browser.public-key-credential` entitlement (Apple grants it per team) is the one a browser needs for platform passkeys — kept from the WKWebView days because it is an app entitlement, though whether CEF's Chromium uses it is unverified. The bundle also registers `http`/`https` (Alternate rank), and URLs handed to the app open as webview tabs (`TermEvent::OpenUrl`).
- `scripts/deploy.sh` — pull main, build, bundle, install to `/Applications`, and install `pwrde-cli` onto PATH (`$PWRDE_CLI_DIR`, else `~/.cargo/bin`, else `/usr/local/bin`). Refuses to run off the `main` branch.

Builds compile through **sccache** (`.cargo/config.toml` sets `rustc-wrapper`), so a fresh worktree's first build pulls the gpui dependency tree from cache instead of recompiling it. sccache must be installed (`brew install sccache`) or cargo fails with "could not execute process `sccache`".

### Chromium (CEF)

Webview tabs render with Chromium through the `cef` crate (cef-rs), which needs the **CEF binary distribution** (~320 MB unpacked: the framework, headers, and the C++ wrapper its build script compiles with `cmake` + `ninja` — `brew install cmake ninja`). cef-rs resolves it from `CEF_PATH`:

- **Recommended:** `export CEF_PATH=~/.local/share/cef` in your shell profile. If the directory has no distribution for the crate's CEF version, the first `cargo build` downloads and unpacks one into `$CEF_PATH/<cef version>/cef_macos_<arch>/` and every worktree and profile then shares it. `cargo install export-cef-dir && export-cef-dir --force ~/.local/share/cef` (cef-rs's own tool) fetches the same thing ahead of time, as a flat directory `CEF_PATH` may also point at.
- **Without `CEF_PATH`** the build script downloads the distribution into cargo's `OUT_DIR` — once per profile per worktree, and gone after `cargo clean`.

At run time `src/cef_app.rs` finds the framework and the helper itself. In `Pwrde.app` they are in `Contents/Frameworks`. For a bare `target/<profile>/pwrde` it uses the distribution the build used (`CEF_PATH` from the environment, else the path baked in at build time) and assembles a stand-in bundle at `target/<profile>/pwrde-cef/Pwrde.app` — a clone of the framework plus the helper apps wrapping `target/<profile>/pwrde-helper` — so `cargo build && cargo run` is enough; no .app needed. If the helper is missing or CEF cannot start, the app still launches and a webview tab reports why in a toast.

`scripts/privacy-usage.plist` holds the privacy usage strings pages can trigger (Bluetooth — any passkey sign-in page probes it — camera, microphone). macOS **aborts** a process that touches one of those services without its string, so a new service a page can reach needs a key there: `build.rs` embeds the file in the bare `pwrde` binary (`__TEXT,__info_plist`, for `cargo run`) and `scripts/make-app.sh` merges it into the bundle's `Info.plist`.
## Architecture

**The README's "Architecture" section is stale.** It describes the original winit + wgpu + glyphon design. The code has since been ported to **gpui** (Zed's UI framework), which is now the sole windowing + rendering layer. `winit`/`wgpu`/`glyphon` still appear in `Cargo.toml` and in port-note comments but are not used by any code. Trust the module doc comments (`//!` headers in each `src/*.rs` file) over the README diagram.

### Dependency pinning constraints

- `wezterm-term` (VT emulation/grid) and `termwiz` (cell/color model) are git dependencies on the wezterm repo and **must be at the same rev** so cell types line up.
- `cef` is pinned to an exact crate version (`=154.3.0`, CEF 154.0.32): the bindings, the framework `scripts/make-app.sh` bundles and the one `pwrde-helper` loads must all be that build. Bumping it means a new CEF distribution in `CEF_PATH`.
- `gpui` and `gpui_platform` are pinned to the same zed repo rev. `gpui_platform`'s `font-kit` feature is **required** — without it gpui falls back to `NoopTextSystem` and no glyphs render (quads still do), which is a confusing failure mode.

### Threading model (per terminal session)

Same shape as iTerm2: a PTY reader thread per session (`term.rs`) reads output in chunks, advances the wezterm-term grid (shared behind `Arc<Mutex>`), and sends a coalesced wakeup — only requested if one isn't already pending — over an mpsc channel drained on gpui's foreground executor. The main thread briefly locks the grid to snapshot visible cells, then paints unlocked. wezterm-term brings no I/O loop, so this reader/coalescing logic is hand-built here.

### Rendering split

Painting happens inside a single custom gpui `Element`'s `paint()` in `main.rs`. `renderer.rs` is deliberately **stateless and GPU-free**: `build_frame` walks the workspace tree + terminal grids and produces a `Frame` of plain data (quads, text runs, labels) that the Element then paints via `window.paint_quad` / `shape_line`. Keep geometry/color logic in `renderer.rs` and actual painting in `main.rs`.

**Exception: Settings** is a real gpui element tree (`settings_ui.rs` etc., built from the vendored rcn components below) living in its own window rather than painted on the canvas. Confirm dialogs stay on the canvas path. The Settings → Appearance section (segmented mode control, the accent swatch row, and the Terminal colors block — a per-polarity theme Select, 20 editable Core/Normal/Bright swatches with hex fields, and a live terminal preview) lives in the overlay too — its previews are element-tree divs painted with the exact theme colors.

### UI components (rcn, vendored in `src/ui/`)

`src/ui/` holds shadcn-style gpui components vendored from [rcn](https://github.com/a1re1/rcn) — "shadcn, but for gpui". Conventions:

- Components are **copied source, not a Cargo dependency** (that's rcn's model). They're pinned to the same gpui rev as the app so they compile unchanged.
- Each file is a port of a shadcn base-vega `ui/*.tsx` component; its `//!` header lists omissions vs the source and any **local additions** (e.g. `Table::h_full`, `TableRow::on_click`, `Badge::color`, `Card::h_full`). When extending a component locally, document the addition in that header and in `src/ui/mod.rs` — this is what keeps future `rcn diff` runs readable.
- Design tokens live in `src/ui/theme.rs` (shadcn's CSS variables as a gpui `Global`). pwrde chrome colors bridge into it via `Theme::from_chrome` — callers `cx.set_global(...)` before rendering rcn components so they track the live chrome theme.
- The **rcn CLI** manages vendoring: `cargo install --git https://github.com/a1re1/rcn rcn-cli`, then `rcn add <component>` to vendor a component (plus registry deps), `rcn list` to see what's installed, `rcn diff <component>` to compare local copies against the registry (useful given the local additions above).
- `rcn.toml` at the repo root maps the registry's default layout onto `src/ui/` (registry components import `crate::theme` / `crate::motion`; ours are `crate::ui::*`). Two consequences: after `rcn add`, rewrite the new file's imports to `crate::ui::…`, and in `src/ui/mod.rs` keep the `pub use` re-exports **above** the `pub mod` lines (`rcn add` regenerates everything after the first `pub mod` and would drop them). **Never run `rcn init` here** — it would overwrite `src/theme.rs` (pwrde's chrome themes) and replace `src/main.rs`.

### Module map

- `main.rs` — gpui app, window, the terminal `Element`, keyboard/mouse handling, tab drag & drop (`DropTarget`/`Drag`).
- `workspace.rs` — group/split-tree/tile/tab model plus pure layout math over the window size, so drawing and hit-testing/PTY-resize always agree. Every group keeps the **primary-pane invariant**, restored by the pure, unit-tested `Workspace::normalize_primary` (run for every group from `App::sync_layout` — the chokepoint after each tree mutation — and on session restore): with more than one tile the root is a `Dir::Row` split whose `a` is `Leaf(primary_tile)` and whose `b` is everything else (a primary found elsewhere is lifted out with `Node::take_tile` and re-wrapped at ratio 0.5; one already in place keeps its ratio; a dangling `primary_tile` is left alone), the primary holds exactly one tab (extras move, in order, to the first tile of the right subtree, or into a new tile split right of a lone primary — which is how a new tab aimed at the primary lands on the right, focus following it). It collapses like any other pane — `Workspace::collapse_axes` reports its real axis (`Dir::Row` in a split, none as a lone root leaf) and normalize leaves its collapse state alone — to the ordinary narrow sideways strip at the left, where it has no title row or info bar. The primary's header is taller — the tab-bar-high title row plus a 48px info bar, both scaled by the chrome factor: `tile_header_h` / `tile_content_for(rect, scale, is_primary)` / `primary_info_bar` / `primary_title_row` (which reserves the caret square when the pane has one) are what PTY sizing, the renderer, mouse hit-testing, webview bounds and drop hints read for a workspace tile (`tile_content` stays for tool pages).
- `term.rs` — `Session`: PTY (portable-pty) + VT emulation (wezterm-term) + reader thread.
- `renderer.rs` — stateless frame building (see above).
- `tile_ui.rs` — tab strips (tiles and, via `tab_strip`, the flyover) as a gpui element tree, to the GANTRY mock: a 40px bar (6px above a 30px row, 4px below), a glass active chip (dimmed and borderless on an unfocused tile) with a terminal glyph — or, on a web tab, the page's favicon clipped to a disc (`App::webview_favicon`; transparent icons are flattened onto a contrasting disc at decode), the globe until one loads — title and ×, text-only inactive tabs sized from a per-character title estimate, hairline separators, and a "+" that opens a tab in that strip. Every strip rect comes from the pure `workspace::tile_strip_layout` / `flyover_strip_layout`, which the canvas mouse path in `main.rs` hit-tests too, so painting and hit-testing cannot disagree. All of those sizes are the figures at the default chrome text size: the whole strip — bar height, row, paddings, width estimates, glyphs and type — scales with `appearance.font_size` by `workspace::chrome_ui_scale()` (the capped factor the sidebar rows use), which the pure `*_at` layout functions take as an argument; tile content, collapsed-tile extents, the flyover body and the traffic-light / show-sessions spots all read the same scaled bar height. The group's primary pane gets no tabs: `primary_title_row` paints the pane title alone (weight 500, ellipsis; no glyph) at `workspace::primary_title_row`'s rects — no chip, × or "+", but the same collapse caret at `tile_caret_rect` whenever the group has more than one tile (`App::press_tile_caret`) — and a press elsewhere on it (or on the info bar) only focuses the pane (`App::press_primary_header`); a right-press on the title row or the info bar opens the pane's native context menu (`MenuTarget::PrimaryHeader`: Split Right with its live binding as the item's shortcut hint — `context_menu::shortcut_for` — then Mark as unread and, when the caret shows, Collapse pane with its binding); collapsed or mid-animation it is the same bare chevron strip as any sideways-collapsed pane, with no title row or info bar; its tab is neither a drag source nor a tab-drop target (edge drops still open a tile, which normalize re-homes on the right).
- `infobar_ui.rs` — the primary pane's info bar (`App::render_info_bar`), an element tree at `workspace::primary_info_bar` under the title row, in the webview toolbar's pill language (32px pills of the `StripStyle` ink at .07, everything × `chrome_ui_scale()`): a repo/branch pill (git only: branch glyph, `repo / branch` or the short SHA when detached, then the committed branch diff as `+A −R` — `GitContext` has no ahead count — and `● N` amber uncommitted files), the cwd pill centred in the remaining space (max 420px, `~`-abbreviated, cut from the left by the pure `truncate_left` to an estimated char budget), a PR pill (state glyph in the sidebar's PR colours, `#N`, Draft/Open/Merged/Closed, checks as `✓ p/t` green / red / dim; a click runs `open_pr_in_github`) and a round unread chip (green dot with a soft ring while the primary tab is unread). The pure `visible_parts` sheds the counts below 620px, the PR pill below 540 and the unread chip below 400 (× the chrome factor). Data is the `App::git_contexts` snapshot keyed by the group's cwd, as the sidebar row reads it — no fetches of its own.
- `webview.rs` / `webview_ui.rs` — webview (browser) tabs. `webview.rs` is the main-thread lifecycle of the native Wry child views (`Manager::sync` reconciles them with the tab model; `toolbar_h()` — `TOOLBAR_H` = 48 scaled by `workspace::chrome_ui_scale()` — and `child_bounds` reserve the GPUI chrome above the page) plus the favicon plumbing: the initialization script posts each page's `link[rel~="icon"]` href and URL over IPC on every load, the pure `favicon_request` validates that into `TermEvent::WebviewFaviconChanged` (falling back to `<origin>/favicon.ico`; a non-http page clears the icon), and `main.rs` fetches it once per icon URL on a background thread (`fetch_favicon`: `/usr/bin/curl` with the URL as one argv element, http(s) only, 5s / 512 KiB caps, decoded and scaled through the `image` crate into a `RenderImage`) into an in-memory cache (`App::favicon_cache`, bounded, never persisted) that the tab strips read through `App::webview_favicon`; a failed, undecodable or SVG icon silently stays the globe. `webview_ui.rs` is the GPUI-owned chrome over each visible webview, to the GANTRY Workspace mock: a 48px bar on the pane ground over a hairline holding a nav capsule (back / forward / reload), a centred address pill (max 420px; the lock / info glyph at its left edge toggles the Site popover, the host alone at rest, the editable full URL once the focused pane's pill is pressed) and a round More button that opens the Tools popover — pills are the theme foreground at .07 and the inks are `tile_ui::StripStyle`'s, so light palettes work. The mock's Annotate and Share-with-agent controls are intentionally absent. The two popovers are floating cards drawn above the page, never reflowing it (`child_bounds` reserves only the toolbar): `App::webview_panel` is the model and `App::webview_popover_card` the element tree, in rcn `Theme` colours with fixed block heights so `card_size` is known without measuring — Site (300px: "Connection is secure / not secure" over `<host> · HTTPS|HTTP`, the live cookie count, Permissions, Certificate, clear data) and Tools (272px: the find field, a zoom stepper whose percentage resets to 100%, open in default browser, copy link, print, developer tools, send page to agent, clear browsing data). Rows without a backend (cookies detail, permissions, certificate, send to agent) answer with a "not available yet" toast. The Tools rows run the rebindable `Action`s `find_in_page` (⌘F: opens Tools with the find field focused), `open_in_browser` (⇧⌘O), `copy_link` (⇧⌘C), `print_page` (⌃⌘P) and `developer_tools` (⌥⌘I) through `App::run_webview_action` — no-ops unless the focused tile's active tab is a webview whose chrome is visible — and show their live bindings as hints; `site_info` (⌃⌘I) toggles the Site popover the same way. The pure `anchor_rect` derives the pill / More rects from the toolbar's own layout constants at the chrome factor; the cards themselves keep their own sizes.
- `webview_popover_window.rs` — the Site / Tools popover's own chrome-less, transparent, card-sized window (a native webview paints over anything the main window draws; modeled on `palette_window.rs`). The 16ms pump calls `reconcile` every tick: it opens the window under its control at the pure, unit-tested `popover_bounds` (Site centred under the address pill, Tools right-aligned under More, 8px gap, clamped to the display), moves it when the anchor moves, reopens it when the panel changes kind or tab, and removes it when `webview_panel` clears. The popover is dismissed by ⎋, its toggle, an action row, its window losing key status (any press elsewhere), its anchor going away (`App::webview_popover_anchor`: tab / tile / group / page change, a modal or the flyover) or the main window moving or closing. Keys go to `App::webview_popover_key`; the find field (`App::webview_find`) takes focus there. Its hidden title (`WINDOW_TITLE`) is how `bus_exec::main_ns_window` keeps `screenshot` / `resize` on the real main window while a popover is key.
- `pages.rs` — top-level pages (`Page`: Sessions, `Tool(i)` per registered CLI tool, Settings (its own window — see `settings_window.rs`) — `Page::all(n_tools)` gives the ⌘⇧←/→ cycling order; there is no page-dot strip any more, tool pages are reached from the folders card and Settings from the gear chip) and rebindable keyboard `Action`s; every ⌘ shortcut resolves through a bindings table from settings keys `keyboard.<action>`. Settings is five sections in order — General, Appearance, Tools, Keyboard, Advanced (`Section::ALL`, default General) — whose `settings_index` / `search_settings` entries back the settings sidebar's search, and `Action::keyboard_group` files every rebindable action into the Keyboard section's five groups (Layout, Tabs & sessions, Focus, Editing, App).
- `sidebar_ui.rs` — the left region as a gpui element tree over the canvas (the GANTRY mock's layout): the flat region ground, the sessions list (header block with the title/"N sessions" subtitle and the show-folders / focus-terminals (`Action::ToggleSidebar`, ⌘S) / ＋ / gear chips, two-line session rows — title · relative time · PR-state icon with the unread dot under it, then "+A −R · N uncommitted", or the cwd and a plain dot for a non-repo), a collapsible "Pinned" run at the top (full rows, sortable; dragging a row across the rail under it pins/unpins, and the caption itself is a drop zone that pins; folded state persists as `sidebar.pinned_collapsed`), and the floating "Show sessions" button while the region is hidden. Rows are absolutely positioned at `workspace::sidebar_row_rect` because the canvas mouse path in `main.rs` hit-tests those same rects for presses and drag-and-drop; the row stack is a wheel-scroll container (`App::sessions_scroll`, clamped by `workspace::max_scroll`), so row helpers take the scrolled `sessions_rows_list` / `rows_list_rect` while the header and clip band keep the unshifted list rect.
- `folders_ui.rs` — the floating glass folders card beside the list (`Action::ToggleFolders`, ⌘; persisted as `sidebar.folders`): pinned CLI-tool rows (click = that tool's page), "All sessions", and one row per section (the mock's *folders*) with member counts; selecting a row sets `App::folder_filter` (persisted as `sidebar.folder`, validated against the sections) which `workspace::sidebar_rows_filtered` applies to the flat list. Folder rows keep inline rename / delete (the ✕ replaces the count on hover), are drop targets for group drags, and are themselves drag-sortable (`Drag::FolderPress`/`Folder` → `DropTarget::FolderInsert` → `workspace::reorder_section`, persisted as the sections' positions); ＋ creates the new group inside the selected folder. The "Pinned tools" caption folds its rows (`sidebar.tools_collapsed`), the card is a wheel-scroll container (`App::folders_scroll`), and its width is a resize band in the card/list gap (`App::folders_w`, session-only like the sidebar width; `resize_ui.rs` arms `Drag::Folders`). Geometry (`folders_card_rect`, `folder_rows`, `folder_row_rect`, `sessions_list_rect`, `sidebar_region_w`, `folders_edge_x`) is pure in `workspace.rs`; `App::sidebar_w()` is the full region width (sessions width + folders column, 0 when collapsed) and `state` reports `sidebar: {collapsed, folders_open, folder, sessions_w, region_w}`.
- `command.rs` / `command_ui.rs` — the unified command palette (⌘P): a pure, unit-tested state machine (root commands grouped + fuzzy-filtered; `New session…` is the multi-step Repo › Base › Layout flow whose picks become token chips, ⌫ pops one) and its rcn element tree on a top-priority deferred layer. ⇧⌘T and the sidebar ＋ open the same palette with the command already committed; the flyover's first-open picker goes through it too. `palette.rs` keeps only `fuzzy_match`.
- `picker.rs` — the palette's step data: the directory scan (`~`, `~/src`, subdirs; git detection; pins/recents in `groups.json`), fork-source choices, and workspace-profile choices.
- `git.rs` — shells out to git for the fork-source picker (default branch, branch lists), mirroring what the `drop` worktree tool runs. Also `worktree_scope`, which settings/persist use to give each linked git worktree its own config/DB.
- `cli_tools.rs` — the CLI tool page registry: `{name, command, cwd, icon}` entries stored as a JSON string under the `tools.cli` setting (absent → the built-in `drop -d` default; `[]` → the user removed it). `main.rs` holds one lazily-spawned `ToolSession` per tool (`ensure_tool_session`, outside the workspace tree so it is never persisted), `renderer.rs::tool_page` paints it as a full-area card, and Settings → Tools (in `settings_ui.rs`) adds/removes entries. The command runs as `$SHELL -lc <command>` (`Session::new`'s `command` arg) so login-shell PATH applies.
- `settings_window.rs` — Settings as its own normal resizable window (960×620, modeled on `palette_window.rs`): a 236px sidebar (a search box over `App::settings_search`, icon nav rows with an "Advanced" caption and row before the last, a pinned `pwrde <CARGO_PKG_VERSION>` footer) beside `App::settings_content`; reconciled by the 16ms pump via `App.settings_open` / `App.settings_window`, closed by ⌘W / Esc.
- `settings_ui.rs` — Settings window content (`App::settings_content`, the window's right pane) as a scrollable column (max-width 720, horizontally centred, no card frame) of captioned blocks: General (sessions + pull requests), Appearance (theme mode/accent, text size steppers, terminal colours as 20 editable swatches — Core/Normal/Bright groups with hex fields — plus one live terminal preview), Tools, Keyboard (rows grouped by `Action::keyboard_group`, click-to-rebind, restore defaults) and Advanced (feature flags + diagnostics); search-results mode reuses the same shell. Keyboard capture (search typing, primary-command and Tools-form Input save/cancel, ⌘-chord recording, and the Appearance hex fields' Enter-commits / Escape-reverts) stays in `main.rs`'s `handle_settings_key`.
- `persist.rs` — session persistence to SQLite (`<data_dir>/pwrde/state.db`, worktree-scoped like settings): group layouts, sidebar sections, shpool sessions. Additive schema migrations in `open_db`.
- `pwrspace.rs` — workspace profiles: saved group layouts in `.pwrspace.json` files, offered when creating a new group.
- `settings.rs` — flat key-value store at `~/.pwrde/settings.json` (worktree-scoped variant under `~/.pwrde/worktrees/<slug>/`); read once at startup, `set` rewrites the file. Load/save are pure functions over an explicit path so tests use temp dirs. A missing/corrupt file must never prevent launch.
- `theme.rs` — chrome colors derived from the accent: `"accent"` (`system` follows macOS's accent color via `NSColor.controlAccentColor`, or one of eight named presets) plus `"appearance.mode"` (system/dark/light) pick one `Theme` per polarity through `from_accent` (the GANTRY mock's recipe — accent mixed into a near-white / near-black ground for the sidebar gradient, white / charcoal cards, fixed ink), applied live. There are no chrome presets or token import/export any more.
- `term_theme.rs` — the terminal palette, separate from chrome themes: 14 ANSI presets plus user-saved custom themes, resolved per appearance polarity into a 20-colour `Palette20` (`bg, fg, cursor, sel, ansi0…ansi15`). `terminal.light` / `terminal.dark` name the base — `"default"`, absent, or unknown all mean wezterm's stock ANSI table on the chrome theme's `term_bg`; `terminal.<polarity>.overrides` stores only the colours that differ from the base as `{key: "#rrggbb"}`, and `terminal.custom` stores saved themes as `{name, label, dark, colors}`. `resolve()` is the pure (unit-tested) resolution — base theme then overrides — and `resolved(dark)` is the settings-reading wrapper every pane renderer calls — renderer, tile chrome, tool pages and `term::TermConfig::color_palette` (the emulator's OSC 4/10/11/12 answers) — so an edit applies live, painted pixels and colour reports alike. Malformed or unknown stored JSON is skipped, never fatal. The two slots a preset does not state keep the pre-existing paint: cursor = effective foreground, selection = the chrome accent (which `renderer::selection_rects` still composites at 30 %).
- `bus.rs` / `bus_exec.rs` / `bin/pwrde-cli.rs` — the command bus. `bus.rs` is the crate-independent wire protocol (JSON-tagged `Command`/`Reply`, NDJSON over a Unix socket at `~/.pwrde/bus.sock` — worktree-scoped like settings — plus `serve`/`request`); it must stay free of `crate::` imports because `pwrde-cli` includes it via `#[path]`. `bus_exec.rs` is `App::execute`, the socket listener's dispatcher; its `Command::Action` arm calls the same `App::run_action` the ⌘P palette and keyboard bindings use (which returns whether the action applied, so the bus can report no-ops), and the other arms cover what the palette can't parameterize: new-session, send-text, focus/move groups, sections, page navigation (`page settings` opens the Settings window), window resize, `state` (JSON snapshot for agents, including `settings_window_open` and `"primary": true` on each group's primary tile) and `screenshot` (in-process `CGWindowListCreateImage` of our own window — no Screen Recording grant needed; `screencapture` is only a fallback; `--window settings` captures the Settings window instead, `--window popover` the open webview popover). `page settings` (or `settings:<section>`) opens the Settings window (`settings_window.rs`) rather than switching pages, and `state` reports `settings_window_open`. Child shells get `PWRDE_SOCKET` so `pwrde-cli` inside a tab targets its own app. Every parameterless UI command is an `Action` (so it is palette-listed and rebindable under `keyboard.<name>`); parameterized mutations plus the `state`/`ping`/`list_commands` introspection commands are bus/CLI-only. The `pwrde-cli read …` namespace is the headless read-only path for agents: `read panes [query]` lists every pane across all groups (flat rows with session id, group, title, foreground process) and `read pane <session-id> [--lines N|--all]` dumps that pane's text plus metadata (title, size, cursor, focus state) — neither changes focus, page, or scroll position. New read-only bus commands get `read_only: true` in their `CommandSpec` and a `read <what>` CLI spelling.
- `flow.rs` / `flow_ui.rs` — the **Flow agent** (experimental, behind the `features.flow` flag in Settings → Feature Flags): a bottom-centered pill bar that expands into a chat panel and drives *this* window through the bus. `flow.rs` is the backend boundary — the `AgentBackend` trait, backend-agnostic `FlowEvent`s delivered as `TermEvent::Flow`, and the pure `FlowState` transcript reducer; `ClaudeCliBackend` (the `claude -p --input/output-format stream-json` child, allowed only `Bash(pwrde-cli:*)`, system prompt = `~/.pwrde/flow-prompt.md` built from the `pwrde-cli` skill) is the only agent-specific code and is meant to be swapped later. `flow_ui.rs` renders the transcript as an element-tree overlay and owns `toggle_flow` (`Action::ToggleFlow`, ⌘J) / `flow_send` (`pwrde-cli flow-send`); `state` reports `flow: {enabled, open, busy, messages}`. While the flag is on, the Sessions/tool-page layouts reserve a bottom safe area (`flow_ui::safe_area_h`, threaded as `terminal_area`'s `bottom_inset` / `ChromeState::flow_inset`) so terminal rows reflow above the pill instead of hiding beneath it, and every Flow size tracks `appearance.font_size` (Settings → Accessibility).
- `features.rs` — experimental feature flags (`features.<key>` settings, default off); `features::ALL` drives the Settings → Feature Flags rows and search entries.
- `claude_hooks.rs` — auto-installs Claude Code hooks (`~/.pwrde/claude-hook.sh`, merged additively into `~/.claude/settings.json`) that emit OSC 9 toasts back onto the pane's PTY so tabs get unread-attention dots.
- `links.rs` — OSC 8 hyperlinks + implicit URL detection over visible lines (hard-wrapped lines are joined before matching).
- `rect.rs` — pure char→geometry mapping for block elements / box-drawing chars and the cursor; painted as gpui quads because fonts can't be trusted to fill the cell.
- `gh.rs` — pull-request summaries for the current branch (`pr list --json`: state, draftness, review decision, mergeability, check rollup, URL), shelled through a settings-configurable CLI: `git.cli` (default `lfg`, swappable to `gh` or any drop-in with the same `pr list --json` contract) and `git.async` (the `lfg -A` fast path). Feeds the sidebar card rollups (`git_context.rs`) and `Action::OpenPrInGithub` (⇧⌘G), which opens the active group's PR in the browser — from the cached rollup when present, else via a background `pr list`. Returns normalized, gpui-free structs; pure JSON-parsing tested inline. (The former right-edge PR / Local-diff / Launch tool panel and its ribbon were removed; there is no in-app diff viewer any more.)
- `lfg.rs` — background tail of `lfg events` (the daemon's cache-updated SSE stream); each event marks the sidebar's git-context rollups stale so PR cards re-fetch when GitHub returns fresh data. Active only on the async `lfg` path.
- `ui/` — vendored rcn components (see "UI components" above).
